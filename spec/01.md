# 01 — Overview, Scope & Non-Goals

## What vexy-dexypy is

vexy-dexypy is an offline-first Python CLI that converts an HTML page into slide
decks. It does not invent slides; it discovers the slides a page already
implies, normalizes the markup, and renders that structure through several PDF
engines at once. Each engine writes its own folder of single-page PDFs. The user
then assembles a final deck by picking the strongest rendering of each slide
across folders.

The core DOM normalization and preprocessing is delegated to a companion JavaScript
package `vexy-dexyjs` running inside the browser context.

## The one-sentence scope

> Fetch an HTML page, classify it, normalize its DOM in the browser via `vexy-dexyjs`,
> paginate it intelligently at a target aspect ratio, render it to PDF through
> several engines in parallel, and slice each result into named single-page PDFs
> and SVGs so the user can cherry-pick slides across strategies.

If a proposed feature is not in that sentence, it needs an argument before it
ships.

## Why multiple strategies

A Webflow hero section renders beautifully through Chromium and badly through a
pure-CSS engine; a text-heavy MkDocs page is the reverse. There is no single
correct pagination — engines disagree on font metrics, margins, and where
content overflows. vexy-dexypy treats that disagreement as the deliverable. One
strategy may produce 11 slides and another 14; that is expected and correct (see
[02](02.md) and [16](16.md)).

## Primary users and use

The author and similar power users, running the tool locally against their own
sites (vexy.art, fontlab.com, blog.fontlab.com) and arbitrary third-party pages.
Output feeds a manual editorial step in a presentation tool of the user's
choice. There is no server, no multi-tenant concern, no auth.

## In scope

- URL and local-file input; full offline operation after the initial fetch.
- Multiple browser reader drivers: standard Playwright, `playwrightauthor` (persistent logged-in sessions via Chrome for Testing), and `cloakbrowser` (stealth-patched Chromium to bypass anti-bot systems).
- In-browser DOM preprocessing and normalization via the JS library `vexy-dexyjs`.
- Framework recognition for Webflow and MkDocs Material first; generic handling
  for everything else; an extensible plugin path for more.
- Viewport-aware pagination at a configurable aspect ratio (default 16:9).
- Parallel rendering via Playwright, Vivliostyle, the native reveal exporter,
  and opt-in Prince.
- Per-slide PDF splitting, optional SVG export (via `vexy-pdfsvgpy`), and a
  reveal.js HTML preview index.

## Non-goals

- **No WYSIWYG slide editor.** Output is files; assembly happens elsewhere.
- **No hosted service, queue, or API.** This is a local CLI ([02](02.md)).
- **No content rewriting or AI authoring.** The optional vision model
  ([10](10.md)) advises on *breaks*, it does not write slides.
- **No universal renderer.** We orchestrate existing engines; we never build a
  layout engine.
- **No crawler.** One page per invocation. (A future multi-page mode is noted in
  [24](24.md) but is out of scope for v1.)

## Anti-bloat rules

These bind every chapter (see also [`../RESEARCH.md`](../RESEARCH.md) and the
project `CLAUDE.md`):

- No analytics, metrics, telemetry, health checks, or production-error
  frameworks.
- No custom caching/retry beyond the simple content-addressed cache in
  [21](21.md) and bounded retries in [22](22.md).
- No class named `Manager`, `Handler`, `System`, or `Framework`. Stages are
  functions or thin classes.
- Build-vs-buy favours maintained packages; custom code only for the
  glue and the genuinely-vexy-dexypy-specific pagination logic ([09](09.md)).

## Success criteria

- `vexy-dexypy build <url>` produces at least one valid per-slide deck folder for
  any of the reference pages without a crash.
- A failed strategy degrades to a warning, never an aborted run ([22](22.md)).
- Adding a new exporter is a plugin, not a core edit ([16](16.md)).
