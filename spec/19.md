# 19 — Stage 5: Slide-Framework Exporter (native reveal.js capture)

When the neutral slides ([11](11.md)) are wrapped in the `reveal` chassis
([15](15.md)), the cleanest path to per-slide PDFs is to drive reveal.js
directly and capture each slide as its own page — no scaling artefacts, no
pagination guesswork.

We do this **natively in Python**, not by shelling out to DeckTape. DeckTape's
reveal capture is a ~30-line plugin over a handful of Reveal API calls; vexy-dexypy
already ships Playwright (the same Chromium it uses for the `playwright`
strategy) and `pypdf` (the writer's splitter). Reimplementing the loop drops the
Node + `decktape` toolchain entirely and keeps the engine on one known-good
Chromium.

## The capture loop

```python
class RevealExporter:
    name = "reveal"; needs_js = True; supports_paged_media = False
    def export(self, job, out):
        with sync_playwright() as p:
            page = p.chromium.launch().new_page(viewport=stage)
            page.goto(job.html_path.as_uri(), wait_until="networkidle")
            page.wait_for_function("() => window.Reveal && Reveal.getTotalSlides() > 0")
            count = page.evaluate("Reveal.getTotalSlides()")
            page.evaluate("Reveal.slide(0,0)")
            for i in range(count):
                buf = page.pdf(width=W, height=H, print_background=True, page_ranges="1")
                writer.append(PdfReader(BytesIO(buf)))
                if i < count - 1:
                    page.evaluate("Reveal.next()")
        writer.write(out)
```

Reveal API surface used (same calls DeckTape's plugin makes):
`Reveal.getTotalSlides()`, `Reveal.slide(h, v)`, `Reveal.next()`. The deck is
initialized with `fragments:false` and all chrome off ([15](15.md)), so
`getTotalSlides()` equals the page count and one `next()` advances exactly one
slide — the loop is deterministic, no `isLastSlide`/fragment edge cases.

## Loading the deck

The exporter opens the localized deck over `file://` (as the `playwright`
strategy already does for the same localized assets, [17](17.md)), so no local
HTTP server is needed. If a future framework's asset resolution misbehaves under
`file://`, a throwaway stdlib `http.server` on an ephemeral port rooted at the
`RenderJob` directory is the fallback — still offline ([07](07.md)).

## Why drive reveal rather than print it

Reveal.js's own `?print-pdf` + browser print works but is fiddly to drive
headlessly and prone to scaling drift. Stepping the deck and capturing each
slide at the locked stage size is deterministic. For Webflow input — already
reveal-shaped via `webflow2reveal` ([12](12.md)) — this is often the
best-looking strategy.

## Future JS frameworks

The same pattern generalizes: an `impress` chassis ([15](15.md)) is captured by
the same kind of step-and-shoot loop against impress.js's API (`impress().next()`),
reusing Playwright + `pypdf`. One small exporter per framework family, no new
external toolchain.

## Relationship to other strategies

The reveal exporter consumes a JS-framework chassis built from the same neutral
slides the paged engines wrap differently ([15](15.md)), and treats slides as
frames rather than pages. It complements rather than competes: a run might emit
`playwright/` (paged), `reveal/` and later `impress/` folders, and the hero
slides often look best from the slide-framework chassis while dense text slides
read best from a paged engine — precisely the cherry-picking the tool exists to
enable ([01](01.md)).
