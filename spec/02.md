# 02 — Architecture & the Six-Stage Pipeline

## The hybrid model

vexy-dex is a Python orchestrator that owns the data model, the CLI, and the
control flow, and shells out to specialized engines for work Python can't do
well. A pure-Python tool cannot see JavaScript-driven layout; a Node-only tool
fights the Fire-CLI requirement. The orchestrator therefore:

- does fetching, parsing, normalization, pagination math, splitting, and
  packaging in-process; and
- spawns subprocesses for Playwright (browser), Vivliostyle CLI, and
  Prince, exchanging files and JSON over stdout/temp files.

This keeps vexy-dex distributable as one Python package while reusing
best-in-class renderers (see [`../RESEARCH.md`](../RESEARCH.md)).

## The six stages

```
URL/file
  │
  ▼  ① READERS            fetch HTML + localize assets        → Source
  ▼  ② PRE-IMPORTERS      classify + plan pagination          → PageDoc + SlidePlan
  ▼  ③ IMPORTERS          framework-specific normalization    → normalized PageDoc
  ▼  ④ PRE-EXPORTERS      inject paged CSS / reveal wrapping   → RenderJob (per strategy)
  ▼  ⑤ EXPORTERS          HTML → multi-page PDF (N engines)    → raw PDF per strategy
  ▼  ⑥ WRITERS            split + SVG + preview index          → DeckResult per strategy
  │
  ▼
out/<slug>/<strategy>/01-*.pdf …
```

Each stage is detailed in its own chapter: readers [06](06.md)–[07](07.md),
pre-importers [08](08.md)–[10](10.md), importers [11](11.md)–[14](14.md),
pre-exporters [15](15.md), exporters [16](16.md)–[19](19.md), writers
[20](20.md).

## Stage contracts

Stages communicate only through the typed artifacts in [03](03.md). A stage
never reaches into another stage's internals. This is what makes a stage
swappable and a strategy independent.

- **Reader**: `Source → PageDoc` (raw HTML + local asset tree).
- **Pre-importer**: `PageDoc → (PageDoc, SlidePlan)` (adds classification +
  break points; never mutates content destructively).
- **Importer**: `(PageDoc, SlidePlan) → PageDoc` (normalized, framework-aware).
- **Pre-exporter**: `(PageDoc, Strategy) → RenderJob` (engine-ready HTML + CSS).
- **Exporter**: `RenderJob → Path` (a multi-page PDF).
- **Writer**: `(Path, Strategy) → DeckResult` (per-slide files + index).

## Fan-out: where divergence lives

The graph is a fan-out: one input → one normalized `PageDoc` → **N strategies**,
each producing its own `RenderJob → PDF → DeckResult`. Strategies are fully
independent and run concurrently ([21](21.md)). Because each engine paginates
differently, decks differ in slide count — by design ([01](01.md), [16](16.md)).

## Plugin boundaries

Readers, importers, exporters, and writers are discovered via
`importlib.metadata` entry points ([11](11.md), [16](16.md)). The core ships the
default set; third parties (or the user) add more without editing core. Each
plugin advertises a `detect(...)` confidence so the orchestrator can auto-select
or run all.

## Determinism and idempotency

A given (URL snapshot, strategy, config) should produce the same deck. The
content-addressed cache ([21](21.md)) keys on the localized `PageDoc` hash plus
strategy + config, so re-runs are cheap and reproducible. Network fetches are
the only non-deterministic step and are isolated in Stage 1.

## Failure isolation

A strategy is a blast-radius boundary. If Vivliostyle segfaults on one page,
Playwright and reveal still produce their decks; the run reports a partial
success ([22](22.md)). The orchestrator never lets one engine's failure abort
the others.
