# 15 — Stage 4: Pre-Exporters

The pre-exporter is the join between a normalized `PageDoc` ([11](11.md)) and a
specific engine's needs. It produces a `RenderJob` ([03](03.md)): engine-ready
HTML plus any CSS the engine requires. Each strategy gets its own `RenderJob`;
the normalized page is shared input.

## Chassis: where divergence becomes real

The pre-exporter takes the **framework-neutral** `<section class="slide">` list
([11](11.md)) and wraps it in a **chassis** — a concrete presentation framework.
The chassis is the product's lever: the same slides rendered through genuinely
different frameworks diverge in layout, scaling, and typography, which is exactly
what the user cherry-picks across ([01](01.md)). A "strategy" is therefore a
*(chassis × engine)* pair, not just an engine.

| Chassis | Wrapping it applies | Engines that consume it | Family |
|---|---|---|---|
| `paged` (default) | neutral sections + `@page`/`break-*` CSS | Vivliostyle, Prince, Playwright | CSS Paged Media |
| `reveal` | `.reveal > .slides`, reveal.js runtime, chrome disabled | native reveal exporter (Playwright) | JS slide framework |
| `impress` *(planned)* | `#impress > .step[data-x…]`, impress.js runtime | same native step-and-shoot loop | JS slide framework |
| `marp` *(planned)* | sections → Markdown front-matter deck | `marp-cli` (own renderer) | Markdown-native |

`paged` and `reveal` ship today; `impress` and `marp` are the first real
alternatives to reveal and are tracked in TODO. A chassis is a small function
`wrap(sections, plan) -> html` plus the assets it localizes; adding one is how
the tool grows a fundamentally different rendering, not just another PDF engine.

Both the `paged` and `reveal` chassis start from the *same* neutral DOM and add
their own scaffolding — neither is privileged in the IR.

## The paged-media stylesheet

One reusable template, parameterized by the stage ([05](05.md)):

```css
@page { size: 1920px 1080px; margin: 0; }
html, body { margin: 0; padding: 0; }
section, .slide {
  break-after: page;            /* modern */
  page-break-after: always;     /* legacy fallback */
  width: 1920px; height: 1080px;
  overflow: hidden; box-sizing: border-box;
}
section h2 { break-before: page; page-break-before: always; }
```

Break points from the `SlidePlan` ([09](09.md)) become explicit
`break-before`/`break-after` declarations where the DOM lacks `<section>`
boundaries, so every engine paginates at the same offsets vexy-dex chose.

## Reveal chassis scaffolding

For the reveal chassis, write a self-contained page with **all UI chrome
disabled** — these are slides destined for PDF/SVG, so navigation arrows, the
progress bar, slide numbers, the help overlay, and the pause overlay must never
appear on a rendered slide:

```html
<link rel="stylesheet" href="reveal.css">
<link rel="stylesheet" href="theme.css">
<style>.reveal .controls,.reveal .progress,.reveal .slide-number,
       .reveal .pause-overlay{display:none!important}</style>
<div class="reveal"><div class="slides">…</div></div>
<script src="reveal.js"></script>
<script>Reveal.initialize({ width: 1920, height: 1080, margin: 0,
  controls: false, progress: false, slideNumber: false,
  controlsTutorial: false, hash: false, help: false, transition: 'none' });</script>
```

The `Reveal.initialize` flags turn the chrome off at the source; the CSS rule is
belt-and-braces in case a plugin or theme re-adds it. reveal.js and its CSS are
bundled (localized, [07](07.md)) so the page renders offline. The `impress`
chassis follows the same rule: no toolbar, no hint overlay.

## Theming

The layout vocabulary classes ([11](11.md)) (`slide-light-bg`,
`slide-image-cover`, …) are styled by a bundled `theme.css`. Keep it small and
neutral; this is not a design system ([01](01.md)). The Webflow importer's own
injected stylesheet ([12](12.md)) covers Webflow-sourced slides.

## Output

The pre-exporter writes the transformed HTML to a strategy-scoped path and
returns a `RenderJob` with `html_path` and `extra_css`. It performs no rendering
— that's the exporter ([16](16.md)). Keeping preparation and rendering separate
is what lets the `render` CLI verb ([04](04.md)) re-run one engine without
redoing normalization.
