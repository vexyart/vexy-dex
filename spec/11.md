# 11 — Stage 3: Importer Framework & Plugin API

Importers turn a classified `PageDoc` ([08](08.md)) plus its `SlidePlan`
([09](09.md)) into a normalized `PageDoc` whose DOM is slide-ready. In
`vexy-dexypy`, the core DOM transformation is executed **in the browser context**
using a companion JavaScript package `vexy-dexyjs`.

## The Python Bridge Contract

Python orchestrates the stage, launching or reusing a browser context (Playwright,
`playwrightauthor`, or `cloakbrowser`), injecting `vexy-dexyjs`, and calling its
APIs. The Python importer contract is:

```python
from typing import Protocol

class Importer(Protocol):
    name: str                       # "webflow", "mkdocs-material", "generic", …
    def detect(self, page: PageDoc) -> float:   # 0..1; agrees with classify (08)
        ...
    def transform(self, page: PageDoc, plan: SlidePlan) -> PageDoc:
        """Injects vexy-dexyjs, runs the preprocessor in-browser, and saves results."""
        ...
```

`transform` runs the browser-side preprocessor, retrieves the normalized HTML/DOM,
and writes it to a new `html_path` (preserving the original for debugging). It must
be idempotent: running it twice yields the same result, and a page already in
canonical form passes through unchanged.

## Discovery

Importers register under the `vexy_dexypy.importers` entry-point group:

```toml
[project.entry-points."vexy_dexypy.importers"]
webflow         = "vexy_dexypy.importers.webflow:WebflowImporter"
mkdocs-material = "vexy_dexypy.importers.mkdocs:MkdocsImporter"
generic         = "vexy_dexypy.importers.generic:GenericImporter"
```

## vexy-dexyjs — The Browser Preprocessor

`vexy-dexyjs` (located in `./vexy-dexyjs/`) is a JavaScript package deployed to NPM
and CDNs. It is a smarter, generalized version of `webflow2revealjs` that can preprocess
ANY page and restructure its DOM into a reveal.js-compatible layout.

### In-Browser JS Execution

The Python bridge invokes the preprocessor inside the browser page context:

```javascript
// Invoked via Playwright page.evaluate()
const config = {
  framework: "webflow",
  stageWidth: 1920,
  stageHeight: 1080,
  breaks: [/* plan.breaks */]
};
const result = await window.VexyDexy.preprocess(config);
// result contains { html: "...", css: "..." }
```

## The canonical layout vocabulary — framework-neutral

Every importer emits the **same framework-neutral structure**: a flat sequence
of `<section class="slide …">` elements, carrying only the shared layout
vocabulary. The IR is *not* a reveal.js deck — reveal is one chassis among
several, applied per-strategy by the pre-exporter ([15](15.md)), not baked into
normalization. This is what makes the divergence between strategies real rather
than cosmetic (reveal vs. impress.js vs. CSS Paged Media are different
*frameworks*, not just different PDF engines — [01](01.md), [16](16.md)).

```html
<section class="slide slide-light-bg">…</section>
<section class="slide slide-dark-bg slide-image-cover">…</section>
```

Layout classes (from the `webflow2reveal` vocabulary, [12](12.md)):
`slide-split-layout`, `slide-column`, `slide-text-container`,
`slide-image-cover`, `slide-badge`, plus `slide-light-bg`/`slide-dark-bg` for
background luminance. The pre-exporter, chassis wrappers, and themes key off
these.

## Respecting the SlidePlan

The preprocessor uses `plan.breaks` to decide section boundaries when the source
lacks explicit `<section>`s — promoting headings at break offsets into
`<section>` starts. Where the framework already has clean sections (Webflow),
the plan validates rather than drives. The two signals reconcile in the
preprocessor.
