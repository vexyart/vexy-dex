# 11 — Stage 3: Importer Framework & Plugin API

Importers turn a classified `PageDoc` ([08](08.md)) plus its `SlidePlan`
([09](09.md)) into a normalized `PageDoc` whose DOM is slide-ready. Each
framework gets its own importer; all share one contract.

## The contract

```python
from typing import Protocol

class Importer(Protocol):
    name: str                       # "webflow", "mkdocs-material", "generic", …
    def detect(self, page: PageDoc) -> float:   # 0..1; agrees with classify (08)
        ...
    def transform(self, page: PageDoc, plan: SlidePlan) -> PageDoc:
        ...
```

`transform` produces normalized HTML written to a new `html_path` (the original
is preserved for debugging). It must be idempotent: running it twice yields the
same result, and a page already in canonical form passes through unchanged.

## Discovery

Importers register under the `vexy_dex.importers` entry-point group:

```toml
[project.entry-points."vexy_dex.importers"]
webflow         = "vexy_dex.importers.webflow:WebflowImporter"
mkdocs-material = "vexy_dex.importers.mkdocs:MkdocsImporter"
generic         = "vexy_dex.importers.generic:GenericImporter"
```

The orchestrator picks the importer whose `name` matches `PageDoc.framework`,
falling back to `generic`. A `detect`-based override is available when the
classifier is unsure.

## The canonical layout vocabulary — framework-neutral

Every importer emits the **same framework-neutral structure**: a flat sequence
of `<section class="slide …">` elements, carrying only the shared layout
vocabulary. The IR is *not* a reveal.js deck — reveal is one chassis among
several, applied per-strategy by the pre-exporter ([15](15.md)), not baked into
normalization. This is what makes the divergence between strategies real rather
than cosmetic (reveal vs. impress.js vs. CSS Paged Media are different
*frameworks*, not just different PDF engines — [01](01.md), [16](16.md)).

```html
<section class="slide slide-light-bg">…</section>
<section class="slide slide-dark-bg slide-image-cover">…</section>
```

Layout classes (from the `webflow2reveal` vocabulary, [12](12.md)):
`slide-split-layout`, `slide-column`, `slide-text-container`,
`slide-image-cover`, `slide-badge`, plus `slide-light-bg`/`slide-dark-bg` for
background luminance. The pre-exporter, chassis wrappers, and themes key off
these.

> **Migration note.** Early code emitted the reveal `<div class="reveal"><div
> class="slides">` wrapper directly from the importer (`dom.wrap_reveal` called
> in `transform`). That conflated the IR with one chassis; the wrapper is now a
> pre-exporter concern. Until the refactor lands (TODO), `dom.wrap_reveal`
> remains but is invoked from the reveal chassis ([15](15.md)), and the neutral
> `<section>` list is the contract every other chassis consumes.

## Parsing tier

- **`selectolax` (Lexbor)** for high-volume traversal/measurement — ~25× faster
  than BeautifulSoup.
- **`BeautifulSoup4 + lxml`** for the readable DOM-surgery code humans maintain
  (extract/wrap/reorder) — what `webflow2reveal` uses.
- **`clear-html`** as an optional pre-pass to flatten div-soup before paged
  engines ([14](14.md), [18](18.md)).

Pick per task; don't mix three parsers in one function.

## Shared helpers

A small `vexy_dex.dom` module provides the reusable operations every importer
needs: `wrap_reveal(soup)`, `split_by_heading(node, level)`,
`drop_chrome(soup, selectors)`, `luminance(color) -> float`. Importers compose
these; they don't each reinvent reveal wrapping.

## Respecting the SlidePlan

The importer uses `plan.breaks` to decide section boundaries when the source
lacks explicit `<section>`s — promoting headings at break offsets into
`<section>` starts. Where the framework already has clean sections (Webflow),
the plan validates rather than drives. The two signals reconcile in the
importer, not later.
